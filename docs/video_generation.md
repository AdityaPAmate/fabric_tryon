## Flow and preserved behavior

Single-image and catalog URLs, validation, image prompts and provider settings keep
their existing contracts. The image view and video worker share the small
`services/tryon_service.py` adapter to the existing `generate_tryon_image` engine.
Catalog generation continues to use its existing runner and streaming protocol.

Video mode accepts every valid existing single-image request: all six garments,
fabric/ready garment, generated/uploaded person, face reference, style, material,
pose, camera, background, details, crop, seed, guidance and draft settings. It first
runs that exact image pipeline, persists the image, uploads it to Gimmeclip, polls
the saved edit, and stores the MP4 in Cloudinary. Image settings affect the source
photo; Gimmeclip does not expose the image engine's seed/guidance controls.

The default inspection motion is unchanged: right fingertips lightly touch fabric once,
then lower to the side; the left arm stays down. The person turns in place to show
the back, then reverses to face front. The prompt uses positive instructions for a
locked camera, continuous shot and unchanged background/light/face/fabric. It does
not invent a mirror setting. The UI offers only Current inspection and Walking /
catwalk. `video_motion` accepts `mirror_check` (default) or `walking`; cached
auto/turn/subtle fields remain ignored. Hand trajectories are still
generated by the provider, not controlled by a pose reference.

Walking has its own saved profile: three slow catwalk steps toward the locked
camera, small natural arm swings, then stand still, preserving the original
framing/background/light/fabric. Both profiles request 8 seconds, the provider's
maximum photo-animation duration; the default PROMPT string is unchanged. Motion
is selected before queuing and saved with the job, not recomputed on retry.
`video_motion` is removed from image inputs so original image generation stays
unchanged. Both generate-tryon-video and animate-image accept the same two choices.

## Advisory continuity check before publishing

An MP4 header is not visual validation. Before Cloudinary upload, the worker now
decodes the existing provider output locally with headless OpenCV. No additional
provider request, model key, queue, service, or UI control is added. The source image
is retained. Successful video metadata includes the continuity check measurements.

The check samples at 4 Hz, removes the first frame's black padding, blurs to reduce
compression noise, and compares the outer 18.75% on each side against the first
frame. Two consecutive samples with median RGB change above 18/255, or median
saturation change at least 15/255 and Lab chroma distance at least 5 OpenCV units,
flag the clip as `video.continuity.status=review_required`. These are engineering thresholds,
tested on the saved examples, not a general-purpose perceptual quality standard.
Undecodable, truncated or oversized-duration/dimension videos are also rejected.

Visual estimates are advisory, not a generation failure. The original clip is
uploaded unchanged and the UI displays it with a prominent review-needed warning;
completion means processing finished, not that garment/background quality was
certified. It never resubmits a paid generation automatically.

Legacy `video_continuity_failed` jobs with a saved provider clip now expose
error.retryable=true. The existing Retry button queues only storage/checking of
that same output, preserving the image, prompt and provider job. Jobs without a
saved clip cannot use this exception to submit a new generation. Double retry
requests are still protected by an atomic compare-and-set.

Scope: this is a conservative edge-continuity heuristic. It catches broad scene,
exposure and saturation changes after the opening frame. It cannot guarantee exact
fabric pattern/colour, unseen back details, hand pose, or changes already present
in the opening frame. Subtle/local edits or changes between samples may pass;
off-centre subjects moving at the edges can be flagged. Passing is not a garment
or identity certification. It does not repair failed footage or composite a new
background, and does not replace visual review.

Historical v1 evidence on 2026-11-24: saved video_0008 (saturation drift) rejected;
video_0009 (job 7567de32-a792-4f27-9d1b-866423ccb13a) and the lab's saved
person10 mirror clip passed. In a broader local run, videos 0001 and 0003-0008
were rejected, and 0002/0009/the lab clip passed. Checks took 0.16-0.74 seconds
locally; Render latency was not measured. V2 preserves those detection thresholds
but reports warnings instead of rejecting playable footage. No new provider generation was used
to establish these results. Fresh output with the v7 prompt is not yet reviewed.

Research references:
- https://gimmeclip.com/openapi.json — photo animation accepts an idea and animate;
  no seed, motion reference, temporal mask or background-lock parameter.
- https://help.runwayml.com/hc/en-us/articles/48324313115155-Image-to-Video-Prompting-Guide
  — focus image-to-video prompts on motion; use clear continuous-shot instructions.
- https://www.scenedetect.com/docs/latest/api/detectors.html — colour/intensity
  differences are useful for detecting transitions. This project uses its own
  conservative outer-frame check, not the PySceneDetect library.

Photo animation in this API supports 4, 6 or 8 seconds, so this flow requests 8
seconds. It does not stretch or loop footage to claim a 10-second result. Reference:
https://gimmeclip.com/openapi.json (EditRecipe.aiEdit.animate).

Each job saves its complete motion profile. Existing accepted/running jobs keep
their original profile; the new prompt applies to newly created jobs. Video quality
and accurate unseen garment details still require visual review of real output.

## API

Video endpoints require `Authorization: Bearer <VIDEO_API_TOKEN>`.
`GIMMECLIP_API_KEY` remains on the server. Without video configuration the existing
image/catalog endpoints still start and work; video endpoints return 503.

- POST `/api/generate-tryon-video/`: original image multipart fields. Returns 202 with job_id/status_url; queues only.
- POST `/api/animate-image/`: multipart `source_image` (PNG/JPEG/WebP), optional
  garment_type, camera_view and pose. Reuses those photo bytes, skipping
  image generation. The UI's "Make video from this image" uploads its selected
  generated single image/catalog shot, not the collage or an arbitrary server URL.
- GET `/api/video-jobs/<uuid>/`: status, image/video, garment_type, fixed motion,
  timing, and error.retryable. Internal paths, provider URLs and keys stay private.
- POST `/api/video-jobs/<uuid>/retry/`: only failed retryable jobs; resumes the same
  image, uploaded Gimmeclip photo, accepted provider edit, or finished MP4 as available.

States: queued -> image_generating -> video_submitting -> video_generating ->
video_storing -> completed (or failed). The short preparing state only persists inputs.
Ambiguous edit submissions cannot be retried blindly. Inspect provider history if
a worker stops after submission but before saving the returned edit ID. Never
repeat a create POST automatically after an unknown response.

`timing` contains elapsed_seconds, total_seconds, image_generation_seconds and
video_generation_seconds. Values are seconds or null. Provider generation time is
submission to observed completion, including queue/poll intervals and worker
pauses; it is not GPU-only time. Existing-photo jobs have no image generation time.

The prototype has a shared operator token, not individual customer accounts.

## Tester UI

The repository copy is tools/tester_ui; the Desktop copy is fabric_tryon_tester_ui.
Choose Single image, Catalog, or Generate video. Image controls remain available.
For video, enter the backend VIDEO_API_TOKEN. Mirror-check motion is fixed.
The result area shows a live total timer and a separate live video timer, progress,
source image, MP4 player, downloads, and saved job UUID. Inspect/resume can recover
polling after refresh; retry appears only when the backend permits it.

Stop waiting cancels browser polling, not the remote generation. Resume the saved
UUID against the same API host. The API URL and last job ID are remembered; the
bearer token is not embedded in HTML or persisted by this UI. On resume, the total
timer starts from the backend's elapsed time. Existing image/catalog reports remain
available and video reports add MP4, job status, and timing.

## Local configuration

Use .env.example for required names; keep actual values in ignored .env only.
Set GIMMECLIP_API_KEY and a separate VIDEO_API_TOKEN. Run:

    python manage.py migrate
    python manage.py runserver
    python manage.py run_video_worker

The worker is sequential and protected by an OS file lock. Web and worker must
share the same database and MEDIA_ROOT. Inputs/generated photos remain in
media/video_jobs for retries; final videos are stored in Cloudinary.

## Render

render.yaml and Dockerfile start web and worker together through
`bash deploy/render-start.sh`. One paid 0.5c-512mb service with a 1 GB /var/data disk
is defined. Keep a single instance. SQLite and retry files need this shared disk;
a separate worker service cannot access that disk. Startup applies migrations at
runtime. Missing optional video keys disables only the worker, keeping image APIs up.

Before deployment push this branch, connect the Blueprint, set Cloudflare,
Cloudinary and Gimmeclip keys, and obtain VIDEO_API_TOKEN from Render Environment.
Use the actual Render service URL in the tester. CORS defaults to localhost:5500
and 127.0.0.1:5500; add the exact tester origin if it uses another port or host.
No Render deploy or paid generation is performed by the code checks.
